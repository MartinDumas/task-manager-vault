# Ізоляція unit-тестів MCP-конектора від робочого vault

## Контекст
`mcp_connector/core.py` реалізує файловий доступ до Obsidian vault і за замовчуванням має `git_sync=True`: перед записом конектор виконує Git pull, а після зміни нотатки — commit і push. Unit-тести зосереджені в `tests/test_connector.py`. Вони перевіряють CRUD, ідемпотентність, валідацію, пошук та окремо поведінку Git-синхронізації.

## Проблема
Тести не повинні читати або змінювати робочий vault, використовувати його нотатки як тестові дані чи випадково запускати pull/commit/push. Прив'язка до реального сховища створює ризик змінити користувацькі дані, залежність від локального стану та мережі, а також робить результати менш відтворюваними.

## Прийняте рішення
Ізолювати файлові перевірки тестового конектора від робочого vault. Для тестів, яким потрібні каталоги й файли, використовувати `tmp_path` pytest-у, створювати там тимчасовий каталог vault і наповнювати його синтетичними нотатками. Для CRUD, пошуку й валідації створювати `VaultConnector(..., git_sync=False)`, щоб ці тести не виконували Git-операцій. Дані формувати локально у тестах (`example()` та fixture-нотатки), не копіювати їх з робочого vault. Git-синхронізацію перевіряти окремим тестом із тимчасовим bare remote і тимчасовими клонами під `tmp_path`, а не з робочим репозиторієм vault.

## Альтернативи
- Використовувати робочий vault як fixture — відхилено через ризик пошкодження даних, залежність від приватного вмісту та нестабільність стану.
- Підмінити файлову систему моками для всіх тестів — відхилено як єдиний підхід: це не перевіряє реальну взаємодію `pathlib` і файлової системи, яку покривають тимчасові каталоги.
- Вимкнути перевірки Git — відхилено: поведінку синхронізації все одно потрібно перевіряти, але лише на ізольованому тимчасовому remote.

## Наслідки
CRUD та пошукові тести мають контрольовані вхідні дані й не залежать від стану Obsidian vault, Git-конфігурації користувача чи мережі. `tmp_path` автоматично надає окрему тимчасову директорію на тест і прибирає її після завершення. `git_sync=False` явно вимикає Git лише в тестах, які перевіряють логіку файлів і нотаток; тест Git-сценарію зберігає перевірку створення commit/push на локальному тестовому remote.

## Ризики та межі
Тимчасовий bare remote перевіряє контракт Git-операцій, але не підтверджує доступність справжнього remote, MCP-дозволи чи працездатність конкретного робочого vault. Ці інтеграційні властивості не є метою unit-тестів і мають перевірятися окремо контрольованими інтеграційними перевірками. Важливо не замінювати тестову директорію шляхом до робочого vault і не вмикати `git_sync=True` у тестах, що не призначені для перевірки Git.

## Статус
Прийнято (`accepted`) після підтвердження користувачем.

## Підстава
У `tests/test_connector.py` файлова fixture створює vault під `tmp_path`; більшість тестів передають `git_sync=False`; Git-сценарій створює тимчасовий bare remote та клони. У `mcp_connector/core.py` з `git_sync=False` метод підготовки Git пропускається, а commit/push повертає `local_only`. Це узгоджується з окремістю vault та вимогою не обходити MCP у `docs/harness-requirements.md` і `docs/guardrails.md`, а також з межею доступу, описаною в [[ADR-004-HarnessAccessBoundary]]. Пов'язано з тестовим компонентом [[TestSuite]] та навігаційною нотаткою [[MOC-Застосунок]].
